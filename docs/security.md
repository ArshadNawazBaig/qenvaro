# Security model

## Trust boundaries

- Sessions use secure HTTP-only cookies. Tenant/store/role/plan/price/stock/total fields from clients are untrusted.
- Inputs are parsed into known primitives with Zod; repositories construct MongoDB expressions and never spread request objects into filters or updates.
- Tenant repositories require trusted server context and always scope queries. Object keys are generated server-side and include non-guessable identifiers.
- Business switch targets are joined back to the signed-in user’s membership. Active-store selections are revalidated against active tenant store assignments before they affect a query.
- Better Auth owns invitation acceptance and membership state. Pending application store grants are tenant-scoped and activated idempotently only for the accepted membership.
- Better Auth verifies the raw Stripe webhook signature and updates its subscription row before invoking Qenvaro’s projection callback. The callback persists event identity/status and updates organization entitlements transactionally and idempotently; failed verified events remain visible for retry.
- Platform identity is a separate global role. A server-only, environment-allowlisted bootstrap is the only implemented assignment path; it requires an existing verified account and revokes sessions on first promotion. The platform role intentionally lacks Better Auth’s request-time `set-role` permission.
- Platform data routes require both Better Auth TOTP enrollment and a second-factor assurance bound to the current session. The enrollment/verification gateway loads no platform data. Expired, revoked, pre-enrollment, and otherwise unassured sessions cannot enter the control plane.
- The platform overview repository exposes counts and grouped tenant entitlement, subscription, verified-webhook, migration, and database-health metadata only. It never queries products, sales, customers, employees, compensation, or other tenant business collections.
- Product detail, edit, and archive derive tenant and store scope from the authenticated membership. Product IDs are re-read with `tenantId` in the mutation transaction, catalog reads require `product:read`, edits/archive require their specific permissions, and expected-version checks reject stale writes. Edit payloads cannot set tenant identity, stock, or archived state; archive retains inventory projections and ledger entries.
- Category reads and mutations derive tenant identity from the same trusted context and re-read category IDs with `tenantId` inside each transaction. Normalized names are unique only within a tenant, expected versions reject stale changes, renames update only that tenant’s active/draft assignments, and archive re-counts assignments before changing state. Category payloads cannot supply tenant identity, assignment counts, lifecycle state, or product selectors.
- Unit reads and mutations derive tenant identity and permissions from the authenticated context. Names and symbols are normalized and uniquely indexed within a tenant, product mutations re-read an active same-tenant unit, expected versions reject stale writes, and archive re-counts active/draft assignments transactionally. Client payloads cannot set tenant identity, assignment counts, default status, or lifecycle metadata.
- Product image uploads run only through an authenticated, same-origin Node route. The route derives tenant and permission context server-side, verifies write entitlement and product ownership before upload, bounds multipart and file size, permits only image MIME types and Cloudinary image formats, and generates opaque provider paths without user file names. Cloudinary secrets never reach the browser. Database attachment is transactional; a failed attachment triggers provider deletion, and failed cleanup is retained for operational recovery.
- Product CSV uploads and mutations use authenticated same-origin routes, server-derived tenant/user/store context, Zod request contracts, strict UTF-8 parsing, bounded files/rows/columns/cells, 30-minute user-owned previews, and database-backed request throttles. Commit revalidates plan limits, tags, SKUs, product versions, and active-store authority transactionally. Existing-SKU updates cannot alter inventory, previews cannot cross users or tenants, and exports include only allowlisted catalog fields with spreadsheet formulas neutralized.
- Inventory reads and mutations derive tenant, user, assigned stores, and permissions from the authenticated context. Adjustment and transfer payloads cannot supply tenant or actor identity; the service re-reads active stores, products, variants, billing entitlement, and level versions in the transaction. Negative stock is denied by default, duplicate request keys cannot double-post, and failed multi-line transfers roll back every projection and movement.
- Product availability input can name only stores from the server-derived assignment scope. The service preserves inaccessible existing assignments, rechecks the product version, blocks archived products, and refuses to hide any non-zero level. Low-stock policy changes require tenant settings permission and an independent expected version; the resulting attention queue is derived only from authorized-store projections and exposes no cross-store notification document.
- Dashboard reads accept only Zod-bounded 7/30-day periods. Sales queries start with the trusted tenant, use the active authorized store for trends and the authorized active-store set for comparisons, and never expose financial values to roles without sales/report permission. The activity query is tenant-scoped, capped at eight records from 90 days, restricted to safe operational actions, and requires audit permission; raw changes and actor details are not projected.
- Customer reads and writes derive tenant and permission context server-side, re-read entity IDs with `tenantId` inside mutation transactions, and reject stale expected versions. Search input is escaped and bounded before repository queries. Client payloads cannot set customer codes, lifecycle state, tenant identity, actor metadata, or normalized search fields. Customer audits deliberately exclude names, emails, phone numbers, addresses, and notes.
- Point-of-sale input is limited to variant references, quantities, discount basis points, expected stock versions, an optional customer reference, recorded tender amounts/methods, a bounded note, and an idempotency key. Completion re-reads the active assigned store, tenant entitlement, active customer, products, variants, availability, inventory levels, prices, costs, taxes, and currency inside the transaction. The server calculates all totals, profit, payment application, and change; a request fingerprint prevents reuse of the same key for changed input. The completed sale, payment records, issued receipt, inventory movements/projections, product revenue, and PII-safe audit commit together or roll back together.
- Return input is limited to an original sale, selected sale-line quantities, expected inventory versions, one recorded refund method, an allowlisted reason, bounded note, and idempotency key. The service re-reads the completed sale, original receipt, active assigned original store, prior completed returns, inventory levels, entitlement, and historical product/variant ownership. Remaining quantities and monetary allocations are server-derived from immutable sale snapshots; exact replay is allowed, changed-key reuse and over-return are denied, and return/refund/receipt/inventory/revenue/sale-summary/audit writes commit together or roll back together.
- Sales-report input is limited to Zod-bounded 7/30/90-day presets, one active assigned store or the assigned-store set, and a bounded transaction page. The repository requires `report:read`; every sales, return, payment, and refund pipeline starts with trusted tenant and authorized store scope plus status/date bounds. Output caps store options, products, transactions, page size, and page number, and incomplete cost evidence suppresses profit instead of leaking or fabricating data.

## Controls

- Email verification, password reset, safe redirects, optional tenant-user 2FA, mandatory platform TOTP, per-session platform assurance, account lockout, and persistent endpoint throttles protect account entry points.
- Product image uploads enforce type, format, and 10 MB size bounds; Cloudinary performs the image-resource validation and a bounded transformation. MongoDB stores only delivery and lifecycle metadata, never image binaries.
- CSV preview uploads enforce a 2 MB and 500-row ceiling, JSON mutation bodies enforce a 64 KB ceiling, and fixed-window limits are shared through MongoDB across application instances.
- Logs and audits omit passwords, tokens, salary values, payment details, and unnecessary PII. Production responses omit stack traces.
- Recorded POS payments persist only method, tendered/applied minor units, provider kind/reference, and lifecycle status. The current manual provider never collects card or wallet credentials, and Stripe remains isolated to SaaS subscription billing.
- Recorded refunds persist only their method, amount, provider kind/reference, return identity, and status. They never store card, bank, or wallet credentials.
- Security headers deny framing and sniffing and restrict browser capabilities. A deployment-specific Content Security Policy must be finalized against its asset providers.
- Production rejects development billing bypass and development seeds.
- Sensitive changes use fresh-session/reauthentication where supported.
- Subscription mutations are authorized twice: Qenvaro requires `billing:manage`, and Better Auth’s organization reference callback independently requires the owner role. Checkout/Portal redirects never grant access.

## Required evidence

Tests cover tenant/store/entity IDOR, privilege escalation, platform-role mass assignment, salary access, plan quota races, webhook replay, invalid workflow transitions, CSV formula injection, and malicious upload metadata. Security findings block release.

Current platform evidence covers configured verified-account bootstrap, unverified-account rejection, idempotent audit, session revocation, exact-role policy, current-session assurance, aggregate-only repository output, TOTP enrollment/re-verification/fresh login, and desktop/mobile accessibility. Product lifecycle evidence covers cross-tenant detail denial, permission enforcement, stale-version rejection, transactional product/default-variant edits, audited idempotent archive, unchanged inventory state, and accessible desktop/mobile browser flows. Product-image evidence covers Cloudinary-only metadata validation, tenant and permission denial, optimistic conflicts, bounded ordering/count, single-primary promotion, audited archive, cleanup state, and responsive read-only rendering. CSV evidence covers strict parsing and formula protection, row-level validation, explicit duplicate behavior, cross-tenant preview denial, plan enforcement, product-version conflicts, atomic new/update/skip results, unchanged inventory for updates, opening-ledger creation for new products, durable jobs/audits, filtered export, and desktop/mobile browser behavior. Inventory evidence covers adjustment and transfer permission denial, tenant/store scoping, optimistic conflicts, negative-stock rejection, idempotent retry, conflicting-key denial, atomic rollback, balanced transfer movements, unchanged tenant-wide totals, store-removal stock guards, availability concurrency/scope preservation, alert-policy permissions/concurrency, live low/out derivation, audits, and accessible responsive workflows. Category and unit evidence covers per-tenant normalized uniqueness, repository isolation, permission denial, stale-write rejection, stable assignments, assignment-aware archive, audit records, and accessible desktop/mobile flows. Customer evidence covers tenant isolation, role denial, bounded search/pagination, stale-write rejection, cross-tenant entity denial, idempotent archive, post-archive edit rejection, safe audit projections, and accessible desktop/mobile workflows. Sale evidence covers server-owned totals and profit, split-tender/change rules, tenant/store/customer/product/permission denial, stale and negative-stock rollback, exact replay and conflicting-key denial, atomic payment/receipt/inventory/revenue/audit writes, scoped receipt reads, and accessible 320 px desktop/mobile checkout. Dashboard evidence covers tenant-local date bounds, active/authorized-store enforcement, cross-tenant exclusion, missing-cost suppression, permission-denied projections, activity allowlisting, accessible chart summaries, and desktop/mobile empty-state behavior. Break-glass tenant access is not implemented and remains disabled.

Return evidence additionally covers cumulative exact allocation, partial/final and archived-SKU handling, over-return prevention, stale rollback, tenant/store/permission denial, exact idempotent replay, atomic return/refund/receipt/stock/revenue/projection/audit writes, scoped history and receipt reads, safe audits, and accessible 320 px browser workflows.

Sales-report evidence covers tenant-calendar boundaries, sale-date versus return-processing-date accounting, tenant/store/report-permission isolation, missing-cost suppression, method/store/product aggregation, bounded combined drill-downs, dedicated indexes, and accessible 320 px desktop/mobile workflows.

This application provides operational reporting and payroll workflows; it does not claim jurisdiction-specific tax, payroll, or statutory-accounting compliance.
